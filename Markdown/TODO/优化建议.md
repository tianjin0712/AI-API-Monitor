# AI API Monitor 优化建议

> 基于 2026-08-13 静态扫描。优先级依据编译/启动、崩溃、核心功能、用户体验、维护成本和扩展性划分。未运行测试，所有“已通过”状态均不作推断。

> 实施更新：已完成趋势刷新同步、预测降级提示、OpenRouter URL 归一化、工具链固定、前端测试基线、Windows CI、Provider HTTP mock 合约测试及数据库损坏安全启动（保留原库副本 + 迁移前快照）；数据库初始化已由无上下文 `expect` 改为带路径和原因的错误传播。面向用户的数据库手动恢复入口与脱敏诊断日志导出仍待继续。

## P0（必须修复）

### 1. 数据库初始化失败时提供可恢复的启动路径

状态：部分完成。数据库损坏（`CORRUPT`/`NOTADB`）已支持保留原库副本并以安全空库启动，迁移前自动快照；面向用户的手动恢复入口与安装版人工验收仍未实现。

- 问题位置：`src-tauri/src/lib.rs`，`Db::open(...).expect("failed to open database")`。
- 当前情况：数据库损坏、目录不可写、磁盘异常或锁问题会直接触发 panic，应用无法展示任何诊断信息。
- 修改方案：让 setup 返回带上下文的错误；记录不含敏感数据的错误原因；在可行时展示“重试 / 打开数据目录 / 备份后重建数据库”的恢复界面。重建必须要求用户确认并先备份原文件。
- 预计收益：避免启动即崩溃，降低数据不可恢复风险和用户排障成本。

### 2. 建立最低自动质量门禁

状态：已完成。

- 问题位置：`package.json` 和仓库级自动化配置；当前没有 CI 文件。
- 当前情况：有 46 个 Rust 单元测试，但没有自动执行证据；也没有前端测试、lint 或统一检查脚本。
- 修改方案：增加只读检查脚本并在 CI 执行 `pnpm install --frozen-lockfile`、`pnpm build`、`cargo fmt --check`、`cargo clippy --all-targets --all-features -- -D warnings`、`cargo test`。缓存依赖但不缓存运行时凭据。
- 预计收益：阻止编译失败、格式问题和后端回归进入主分支，为后续优化提供可靠基线。

## P1（建议优化）

### 1. 刷新完成后同步更新趋势和预测

状态：已完成。

- 问题位置：`src/pages/Dashboard.tsx`、`src/components/TrendWidget.tsx`。
- 当前情况：刷新命令会更新 SQLite，但 TrendWidget 的 `load()` 只依赖账户 ID；同页刷新后图表仍可能显示旧历史和旧预测。
- 修改方案：由 Dashboard 维护 `historyRevision` 或刷新完成时间并传给 TrendWidget；刷新成功后递增，由 TrendWidget 重新加载。也可把历史状态提升到 Dashboard 并统一刷新。
- 预计收益：Dashboard 数据一致，用户无需切换页面/账户才能看到最新趋势。

### 2. 修正“无法预测”状态判断

状态：已完成。

- 问题位置：`src/components/TrendWidget.tsx:142-168`、`commands.rs::predict_for`。
- 当前情况：Provider 存在时通常返回 Prediction 对象，即使 `samples === 0`、`balance === null` 或 `daysLeft === null`；当前降级文案只在 `prediction === null` 时出现。
- 修改方案：以 `prediction.samples === 0 || prediction.balance === null || prediction.daysLeft === null` 区分原因；仅在样本和余额有效时突出耗尽预测，并保留历史图。
- 预计收益：避免 `0.00 / — / —` 的含糊结果，解释平台数据缺失而非误导为零消耗。

### 3. 归一化 OpenRouter Base URL

状态：已完成。

- 问题位置：`src-tauri/src/providers/openrouter.rs::key_url`。
- 当前情况：函数无条件追加 `/api/v1/key`；用户若填写常见 Base `https://openrouter.ai/api/v1`，会得到 `/api/v1/api/v1/key`。现有单元测试甚至固定了这一结果。
- 修改方案：定义并测试可接受输入：站点根、`/api/v1`、完整 `/api/v1/key` 均归一为一个端点；或在后端校验中只接受站点根并给出明确错误。前后端提示必须一致。
- 预计收益：减少配置正确但刷新 404 的问题，提升自定义网关兼容性。

### 4. 增加前端组件与调度测试

状态：部分完成。已引入 Vitest 并覆盖预测状态与布局兼容逻辑；组件交互和 fake timer 调度测试仍待补充。

- 问题位置：`src/`，当前无 `*.test.*` / `*.spec.*`。
- 当前情况：刷新单飞、计时器重置、快速切换账户、布局防抖和菜单键盘操作都依赖人工回归。
- 修改方案：引入 Vitest + React Testing Library + fake timers；优先覆盖 Dashboard 刷新、TrendWidget 竞态/降级、Settings 校验、layout 解析和 format 边界。
- 预计收益：降低 UI 竞态和数据陈旧回归，支持安全拆分大型组件。

### 5. 建立 Provider HTTP mock 合约测试

状态：已完成。

- 问题位置：`src-tauri/src/providers/*.rs`。
- 当前情况：现有测试主要解析静态 JSON 和纯函数，真实 HTTP 状态、分页、超时、认证头及异常 body 的端到端适配器路径覆盖有限。
- 修改方案：使用本地 mock server，逐适配器覆盖成功、401/403、429、5xx、超时、分页上限、字段缺失、NaN/负数和协议变化；禁止在测试中使用真实 Key。
- 预计收益：更早发现外部 API 漂移，减少真实账户回归成本和费用风险。

### 6. 明确并持久化通知去重策略

- 问题位置：`commands.rs::AlertState`。
- 当前情况：提醒状态只保存在内存，应用每次重启后首次低额度刷新都可能再次通知。
- 修改方案：明确“每进程一次”还是“跨重启去重”；若需跨重启，将级别和最后通知时间写入 settings，并设计恢复阈值与冷却时间。
- 预计收益：减少重复通知，同时保留额度进一步恶化时的关键提醒。

### 7. 统一 Provider 元数据

- 问题位置：`Settings.tsx` 的 `TYPE_PRESETS` / `NO_API_KEY_TYPES` / `TYPE_HINTS` 与 Rust 注册表。
- 当前情况：类型列表动态来自后端，但默认 URL、凭据方式和提示仍硬编码在前端；新增平台要跨多处同步。
- 修改方案：让后端返回 Provider descriptor（类型、显示名、默认 URL、能力、凭据模式、实验状态、提示），前端按描述生成表单。
- 预计收益：减少配置漂移，新增 Provider 更接近单点注册。

## P2（长期优化）

### 1. 拆分大型模块

- 问题位置：`commands.rs` 783 行、`Settings.tsx` 477 行、`Dashboard.tsx` 434 行。
- 当前情况：刷新、统计、通知、布局和窗口命令集中；页面同时承担数据、调度和渲染。
- 修改方案：Rust 拆为 refresh/history/prediction/alerts 命令服务；React 拆为 hooks（refresh scheduler/provider data）和独立表单/Widget 编辑组件。
- 预计收益：降低耦合，缩小测试单元，提高多人开发与代码审查效率。

### 2. 自动生成前后端传输类型

- 问题位置：`src/types.ts` 与 Rust structs。
- 当前情况：DTO 双份维护，依靠人工保证 camelCase、可空性和数值类型一致。
- 修改方案：评估 specta/tauri-specta 或 JSON Schema 生成；至少增加契约快照测试。
- 预计收益：减少字段漂移导致的运行时空值和序列化错误。

### 3. 固定开发工具链

状态：已完成。

- 问题位置：仓库根目录与 `package.json`。
- 当前情况：缺少 `packageManager`、Node engines、`.nvmrc`/Volta 配置和 `rust-toolchain.toml`。
- 修改方案：根据 CI 验证结果固定 pnpm、Node LTS 和 Rust stable 版本，并写入维护文档。
- 预计收益：提高新环境、CI 和发布构建的可复现性。

### 4. 明确日历日与时区口径

- 问题位置：`commands.rs::record_usage`、历史 SQL、预测耗尽日期及 Provider 日聚合。
- 当前情况：统一使用 UTC 日期；非 UTC 用户在本地午夜附近可能把“今日”理解为另一天。
- 修改方案：先决定产品按平台 UTC 账期还是用户本地日历日；在 schema/设置中保存时区口径，迁移前评估历史兼容性，UI 显示所用时区。
- 预计收益：避免跨时区统计争议，提升日报与预测可信度。

### 5. 清理脚手架品牌与未用资源

状态：已完成页面标题/favicon 替换，并删除未使用的 Vite/Tauri 模板 SVG；其他平台打包图标仍按发布矩阵保留。

- 问题位置：`index.html`、`public/vite.svg`、`public/tauri.svg`、部分图标。
- 当前情况：HTML 标题仍是模板名称，favicon 是 Vite；Tauri SVG 无引用；部分平台图标仅凭静态配置无法确认用途。
- 修改方案：将标题/favicon 替换为产品品牌；确认打包矩阵后删除确定未用资源。删除前保留版本控制恢复能力。
- 预计收益：统一品牌，减少资源噪声和后续 AI/开发者误判。

### 6. 提升布局交互与可访问性

- 问题位置：Dashboard 的 HTML5 `draggable` Widget 排序。
- 当前情况：鼠标可拖拽，但触控与纯键盘排序能力不足。
- 修改方案：增加上移/下移按钮和 ARIA live 提示，或采用支持指针/键盘传感器的排序方案；保留布局校验与向前兼容。
- 预计收益：改善触控、键盘和辅助技术用户体验。

### 7. 数据诊断、备份与恢复

- 问题位置：SQLite、keyring、Provider 错误处理。
- 当前情况：有错误文本但缺少统一诊断导出；数据库恢复流程未实现。
- 修改方案：提供脱敏诊断报告（版本、schema、Provider 类型、错误分类，不含 Key/完整敏感响应）、数据库备份与迁移前快照；恢复操作必须显式确认。
- 预计收益：缩短支持响应时间，降低迁移和数据库故障的数据风险。

## 建议验收顺序

1. 建立 CI 基线并记录当前结果。
2. 修复启动失败路径、趋势刷新和预测提示。
3. 增加前端测试与 Provider mock 测试后，再拆分模块。
4. 固定工具链和 Provider 元数据合约。
5. 最后推进时区、完整 DIY、诊断备份等架构性工作。
