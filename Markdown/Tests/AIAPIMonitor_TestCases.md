# AIAPIMonitor 测试用例

## 测试概要

| 项目 | 内容 |
|---|---|
| 项目名称 | AI API Monitor（`ai-api-monitor`，V0.5-alpha / 0.1.0） |
| 测试用例总数 | 50 |
| 优先级分布 | P0：21；P1：24；P2：5 |
| 测试类型分布 | 正常：22；异常：16；网络：8；UI：14；稳定性：12；安全：9；兼容性：6；边界：7（按“包含该类型”统计；同一用例可兼具多种类型，因此不相加为 50） |
| 建议环境 | Windows 10/11 + WebView2；macOS 需在已签名构建产物上复测桌面行为 |
| 测试数据 | 仅使用测试账户和虚拟密钥，例如 `sk-test-xxxxxxxx`；不得录入真实生产密钥到文档、截图或缺陷单 |

## 当前测试范围

本用例集以当前源码为准，覆盖已注册的 `claude`、`codex`、`deepseek`、`openai`、`openrouter`、`siliconflow` Provider；Provider 配置与系统凭据库、SQLite 历史数据、前后台自动刷新、手动刷新、趋势与预测、系统通知、主题/主题色/布局保存、Full/Mini/Ball 窗口、托盘、置顶、窗口几何恢复，以及更新检查界面的当前行为。

网络异常建议使用本机 HTTP Mock（回环 HTTP 为当前实现允许的唯一 HTTP 地址）、防火墙或可控 DNS 环境构造。真实 Provider 的字段和权限以测试时官方接口为准。

## 暂未测试

- Gemini 没有注册到 Provider 列表，当前不能添加或查询；不设计其正向功能用例。
- Widget 的自由定位、缩放、透明度、圆角、字体大小编辑与鼠标穿透/自动隐藏尚未实现。
- 更新插件虽已接入命令，但 `tauri.conf.json` 的公钥和更新源为空，无法对真实下载、签名校验和安装流程做端到端验证。
- 当前没有应用内诊断日志导出、数据库备份/恢复入口，无法从 UI 验证这些能力。
- macOS 的 Keychain、通知权限、DMG 签名与安装包升级需在 macOS 真机及签名产物上执行；本仓库 CI 主要面向 Windows。

# 测试用例

## TC-001 首次启动显示空状态

- 模块：启动与总览
- 优先级：P0
- 测试类型：正常、UI
- 使用场景：用户首次安装后打开应用，尚未添加任何 API 账户。
- 前置条件：使用全新的应用数据目录，系统中无运行中的 AI API Monitor。

### 操作步骤

1. 启动应用并等待界面稳定。
2. 查看总览、设置页和系统托盘。
3. 切回总览。

### 预期结果

1. 默认进入 Full 模式总览，未崩溃、无空白页。
2. 总览显示“尚未添加 Provider”引导，设置显示“暂无账户”。
3. 默认暗色主题、无边框窗口和托盘图标均可见。

### 失败判定

- 启动失败、无托盘图标、空账户时出现无处理异常或误显示历史账户即失败。

## TC-002 日常启动恢复已保存账户

- 模块：启动、配置持久化
- 优先级：P2
- 测试类型：正常、稳定性
- 使用场景：用户早上开机后再次打开前一天已配置好的应用。
- 前置条件：已有两个有效账户、已保存刷新策略和布局；前次通过托盘“退出”结束。

### 操作步骤

1. 启动应用。
2. 查看设置中的账户数、刷新策略和置顶开关。
3. 返回总览并等待首轮刷新。

### 预期结果

1. 账户只恢复一次，名称、类型、URL 与上次保存一致，Key 不显示。
2. 设置值和布局恢复，不被默认值覆盖。
3. 总览对已恢复账户自动发起刷新。

### 失败判定

- 账户丢失、重复、配置回退默认，或启动后不刷新任何已有账户即失败。

## TC-003 添加 DeepSeek 日常账户并查询余额

- 模块：Provider 管理、DeepSeek
- 优先级：P0
- 测试类型：正常
- 使用场景：用户添加常用 DeepSeek 充值账户查看剩余人民币余额。
- 前置条件：准备可用的 DeepSeek 测试 Key 和可访问网络。

### 操作步骤

1. 在设置中填写名称“DeepSeek 日常”，选择 `deepseek`，保留预置 HTTPS URL。
2. 输入 `sk-test-xxxxxxxx` 形式的测试 Key 并添加。
3. 回总览，刷新该账户。

### 预期结果

1. 账户创建成功并显示在列表与卡片中。
2. 卡片展示平台返回的余额和币种；没有公开 Token/费用字段时显示“—”，不显示伪造的 0。
3. 更新时间在刷新成功后更新。

### 失败判定

- 无法创建、余额串到其他账户、未知字段被作为真实 0 展示即失败。

## TC-004 添加 Codex CLI 登录态账户

- 模块：Provider 管理、Codex
- 优先级：P0
- 测试类型：正常、安全
- 使用场景：已使用 Codex CLI 登录 ChatGPT 的用户查看订阅额度。
- 前置条件：本机 `~/.codex/auth.json` 有有效登录态且可访问 chatgpt.com。

### 操作步骤

1. 在设置中选择 `codex`，填写账户名称。
2. 检查 Base URL 与 API Key 控件状态后添加。
3. 刷新该账户。

### 预期结果

1. Base URL 固定为官方 Codex 地址且不可编辑，API Key 输入不出现。
2. 不写入新的 API Key 凭据，账户可保存。
3. 成功时展示 credits/剩余百分比/重置时间中的可用数据，credits 不被当作货币。

### 失败判定

- 用户可将 Codex 令牌请求指向任意地址、要求填写 Key，或把 credits 汇总为人民币/美元即失败。

## TC-005 Codex 登录失效后的可行动错误

- 模块：Codex、错误提示
- 优先级：P0
- 测试类型：异常、安全
- 使用场景：用户的 CLI 登录态过期，打开应用时仍希望知道如何恢复。
- 前置条件：已有 Codex 账户；删除/失效化测试环境的 `auth.json`，或 Mock 返回 401/403。

### 操作步骤

1. 刷新 Codex 账户。
2. 观察该卡片和其他 Provider 卡片。
3. 执行 `codex login` 恢复有效登录态后再次刷新。

### 预期结果

1. 该卡片显示登录过期/凭据无效及重新登录提示。
2. 其他账户仍可刷新和显示数据。
3. 恢复登录后该卡片可再次成功刷新。

### 失败判定

- 整个总览被阻塞、错误泄露 access token，或恢复登录仍无法刷新即失败。

## TC-006 添加 OpenRouter 并验证 URL 归一化

- 模块：OpenRouter、Provider 配置
- 优先级：P1
- 测试类型：正常、边界
- 使用场景：用户从不同文档复制了站点根、`/api/v1` 或完整 key 地址。
- 前置条件：准备有效 OpenRouter 测试 Key；可使用 HTTP Mock 记录实际请求路径。

### 操作步骤

1. 分别以站点根、`/api/v1`、`/api/v1/key/` 创建/编辑测试账户。
2. 每次刷新账户并记录请求 URL。
3. 查看余额、今日费用、月费用和重置时间。

### 预期结果

1. 三种写法均只请求一次 `/api/v1/key`，不重复拼接路径。
2. 费用字段显示为美元费用，不误作 Token。
3. `limit_remaining` 缺失时余额显示未知而非错误 0。

### 失败判定

- 请求 URL 错误、重复 `/api/v1`、费用被填入 Token 或无限额度被显示为零即失败。

## TC-007 添加 SiliconFlow 并处理业务错误

- 模块：SiliconFlow
- 优先级：P0
- 测试类型：正常、异常
- 使用场景：用户查看硅基流动余额，平台有时返回 HTTP 200 但业务码失败。
- 前置条件：准备有效 Key；Mock 可返回 `code=0` 和非零 `code`。

### 操作步骤

1. 添加 `siliconflow` 账户并刷新成功响应。
2. 令 Mock 返回 HTTP 200、`code` 非 0、`message` 为“Token is invalid”。
3. 重新改回成功响应并刷新。

### 预期结果

1. 成功响应展示人民币余额。
2. 非零业务码以 message 显示在该账户错误区域，不写入伪余额。
3. 恢复成功后错误消失、余额更新。

### 失败判定

- HTTP 200 被无条件视为成功、业务错误覆盖其他账户，或错误恢复后残留失败状态即失败。

## TC-008 Claude 管理员 Key 与后付费展示

- 模块：Claude
- 优先级：P1
- 测试类型：正常、UI
- 使用场景：组织管理员查询 Claude 的用量与成本，不查询不存在的预付余额。
- 前置条件：Anthropic Organization Admin 测试 Key，或可复现 Usage/Cost API 的 Mock。

### 操作步骤

1. 选择 `claude` 并检查管理员 Key 提示。
2. 添加账户后刷新，Mock 返回 30 天 usage/cost 分页数据。
3. 查看账户卡片、费用概览和趋势。

### 预期结果

1. 页面提示个人 Key 不适用。
2. Token 与 cents 转换后的美元费用正确，余额显示“—”。
3. 有当日 bucket 时记录今日 Token/费用；无当日 bucket 时保持未知。

### 失败判定

- 后付费账户显示余额 0、成本未除以 100，或无当日 bucket 被记录为真实 0 即失败。

## TC-009 自定义 OpenAI Admin 兼容服务

- 模块：Custom Provider、OpenAI 适配器
- 优先级：P1
- 测试类型：正常、兼容性
- 使用场景：公司有同时实现 OpenAI Organization Usage 与 Costs 接口的私有网关。
- 前置条件：本机回环 Mock 提供兼容的两个 Organization 接口和测试 Key。

### 操作步骤

1. 选择 `custom`，填写本机回环 URL 与虚拟 Key。
2. 添加并刷新。
3. 查看 30 天 Token、今日费用、月费用及历史。

### 预期结果

1. 本机 HTTP 地址校验通过，远程 HTTP 不在本用例范围内。
2. 数据按 OpenAI Admin schema 聚合并保存。
3. 未实现两个 Organization 端点的普通 Chat Completions 网关应返回可读错误。

### 失败判定

- 将普通 Chat Completions 兼容误判为支持，或自定义账户影响已配置官方 OpenAI 账户即失败。

## TC-010 Provider 类型白名单与 Gemini 不可添加

- 模块：设置、Provider 注册
- 优先级：P0
- 测试类型：异常、安全
- 使用场景：用户尝试添加文档中提及但当前没有公开用量接口的平台。
- 前置条件：打开设置页。

### 操作步骤

1. 展开 Provider 类型列表。
2. 确认是否包含 Gemini 和未注册随机类型。
3. 通过调用层/篡改输入尝试提交 `gemini` 或 `unknown-provider`。

### 预期结果

1. UI 仅列出当前注册的六种类型及 `custom`（如已注册）。
2. Gemini 不可从 UI 添加。
3. 后端拒绝未注册类型，不创建数据库记录或凭据。

### 失败判定

- Gemini 被作为可用监控账户创建，或任意自造类型绕过白名单即失败。

## TC-011 新增账户必填和安全 URL 校验

- 模块：Provider 配置校验
- 优先级：P0
- 测试类型：异常、安全
- 使用场景：用户误漏填字段或粘贴了非加密公网地址。
- 前置条件：进入新增账户表单。

### 操作步骤

1. 分别提交空名称、空 URL、非 Codex 的空 Key。
2. 填写 `http://example.com` 后提交。
3. 填写 `ftp://example.com` 后提交。

### 预期结果

1. 前端给出必填提示且不清空已填其他字段。
2. 后端拒绝远程 HTTP 和非 HTTP(S) 协议。
3. 失败提交不新增账户，也不遗留可用凭据记录。

### 失败判定

- 无效配置可保存、远程 HTTP 可通过，或失败后账户/密钥残留即失败。

## TC-012 编辑账户但保留原 API Key

- 模块：账户编辑、凭据存储
- 优先级：P2
- 测试类型：正常
- 使用场景：用户只想把“DeepSeek 主账户”改名为“DeepSeek 工作”。
- 前置条件：已有可刷新成功的非 Codex 账户。

### 操作步骤

1. 点击编辑，仅修改名称或合法 HTTPS URL。
2. 保持 API Key 输入为空并保存。
3. 返回总览刷新该账户。

### 预期结果

1. 账户元数据更新，编辑页提示“留空表示不修改”。
2. 旧 Key 仍然有效，刷新成功。
3. 列表和响应中始终不回显 Key。

### 失败判定

- 空 Key 被理解为删除 Key、刷新认证失败，或 Key 被回显即失败。

## TC-013 更换已过期 API Key 并恢复

- 模块：账户编辑、认证恢复
- 优先级：P1
- 测试类型：异常、正常
- 使用场景：平台轮换 Key 后，用户在不删除历史账户的情况下更新凭据。
- 前置条件：账户因 401 显示失败；准备新有效测试 Key。

### 操作步骤

1. 在总览确认该账户认证失败。
2. 在设置中编辑该账户，输入新 Key 并保存。
3. 返回总览手动刷新。

### 预期结果

1. 新 Key 覆盖旧凭据，账户 ID、历史关联和布局不变。
2. 刷新成功后清除该卡片错误。
3. UI、SQLite 和错误文本中均无完整旧/新 Key。

### 失败判定

- 新 Key 未生效、旧历史丢失、错误不清除或任何位置泄露 Key 即失败。

## TC-014 取消删除账户

- 模块：账户删除
- 优先级：P2
- 测试类型：UI
- 使用场景：用户误点删除，意识到该账户仍在使用。
- 前置条件：至少有一个可刷新账户。

### 操作步骤

1. 点击该账户“删除”。
2. 在浏览器原生确认框中选择取消。
3. 回总览刷新该账户。

### 预期结果

1. 账户仍在设置列表和总览中。
2. 其 Key 未清除，刷新仍成功。
3. 其他账户不受影响。

### 失败判定

- 取消仍删除数据/凭据，或取消后账户不可刷新即失败。

## TC-015 确认删除账户与凭据清理

- 模块：账户删除、系统凭据库
- 优先级：P0
- 测试类型：安全、稳定性
- 使用场景：用户不再使用某个测试平台，需要彻底移除本地配置。
- 前置条件：已有非 Codex 测试账户，可检查系统凭据库或用可控 keyring Mock。

### 操作步骤

1. 确认删除该账户。
2. 检查设置、总览和系统凭据库中对应唯一引用。
3. 重启应用。

### 预期结果

1. 账户从数据库列表、总览卡片中消失。
2. 凭据删除成功时返回已清理状态。
3. 重启后账户不会恢复，其他账户与其凭据不受影响。

### 失败判定

- 删除后账户重现、凭据仍可被读取，或误删其他同名账户凭据即失败。

## TC-016 凭据清理失败必须可见

- 模块：账户删除、错误提示
- 优先级：P0
- 测试类型：异常、安全
- 使用场景：系统凭据库暂时拒绝删除，用户需要知道残留风险。
- 前置条件：通过 keyring Mock 或权限控制制造凭据删除失败。

### 操作步骤

1. 确认删除对应账户。
2. 观察删除后的设置页提示。
3. 重启并确认账户数据库记录状态。

### 预期结果

1. 账户记录删除，避免继续使用该配置。
2. 界面明确提示凭据清理失败及可能残留，不能静默显示完全成功。
3. 提示不包含完整 API Key。

### 失败判定

- 凭据失败被吞掉、账户仍显示，或错误文本暴露 Key 即失败。

## TC-017 批量刷新时 Provider 成功/失败隔离

- 模块：刷新调度、Provider 隔离
- 优先级：P1
- 测试类型：异常、网络
- 使用场景：用户早上同时查看多个平台，DeepSeek 正常而另一个平台网络失败。
- 前置条件：配置三个账户；Mock 使一个成功、一个 401、一个超时。

### 操作步骤

1. 点击“立即刷新”。
2. 等待所有请求结束。
3. 查看三张卡片和趋势刷新状态。

### 预期结果

1. 成功账户更新数据并写入历史。
2. 两个失败账户分别显示各自错误，旧成功数据不被其他账户覆盖。
3. 页面整体保持可用，趋势可对成功账户重新读取。

### 失败判定

- 一个失败导致整批无结果、卡片数据串位、或成功结果未保留即失败。

## TC-018 单账户刷新不干扰其他账户

- 模块：手动刷新
- 优先级：P1
- 测试类型：正常
- 使用场景：用户只想确认某个余额刚充值的账户。
- 前置条件：至少两个账户均已有成功数据显示。

### 操作步骤

1. 记录两张卡片的更新时间。
2. 只点击其中一张卡片的“刷新此账户”。
3. 等待完成。

### 预期结果

1. 仅目标卡片进入刷新态和更新时间变化。
2. 非目标卡片的数据、错误及更新时间不变化。
3. 目标成功后仅清除其自身旧错误。

### 失败判定

- 单卡刷新触发所有账户、更新错卡，或目标错误无法清除即失败。

## TC-019 自动刷新、前后台间隔与单飞

- 模块：自动刷新
- 优先级：P0
- 测试类型：稳定性、网络
- 使用场景：用户全天打开监控器，前台工作、随后切换到其他应用。
- 前置条件：至少一个 Mock Provider 可记录请求时间；设置前台 10 秒、后台 60 秒。

### 操作步骤

## TC-042 长时间运行后的刷新与内存状态

- 模块：稳定性、刷新监听器
- 优先级：P2
- 测试类型：稳定性
- 使用场景：用户让应用连续运行一整天监控额度。
- 前置条件：使用稳定 Mock Provider，前台刷新 10 秒、后台刷新 60 秒；可观察进程资源和请求数。

### 操作步骤

1. 前后台交替运行至少 8 小时，期间多次切换总览/设置、Mini/Ball。
2. 定期检查请求频率、内存和刷新状态。
3. 最后手动刷新并查看趋势。

### 预期结果

1. 刷新持续执行且不随页面/模式切换倍增。
2. 没有明显持续增长的内存、事件监听或定时器泄漏迹象。
3. 最终手动刷新和页面操作仍可正常完成。

### 失败判定

- 请求数逐步倍增、内存持续异常增长、卡死或长运行后无法刷新即失败。

## TC-043 异常退出后 SQLite 与配置可恢复

- 模块：数据持久化、启动恢复
- 优先级：P0
- 测试类型：稳定性、安全
- 使用场景：电脑蓝屏、被任务管理器结束或断电后，用户再次打开应用。
- 前置条件：已有账户、布局、刷新策略和历史数据；使用测试环境。

### 操作步骤

1. 在一次刷新/布局保存后强制结束应用进程。
2. 再次启动应用。
3. 查看账户、布局、历史和可刷新性。

### 预期结果

1. 应用能打开 SQLite（WAL）并进入可用界面。
2. 已完成提交的账户/设置/历史仍存在；未完成写入不会造成数据库损坏。
3. 凭据仍只由系统凭据库引用，未出现在数据库明文列中。

### 失败判定

- 无法启动、数据库损坏、已提交数据大量丢失或 Key 明文落库即失败。

## TC-044 API Key 不在 UI、SQLite、普通错误中泄露

- 模块：凭据安全
- 优先级：P0
- 测试类型：安全
- 使用场景：用户在共享电脑上查看账户状态，或提交错误截图给支持人员。
- 前置条件：添加两个同名、不同 Key 的非 Codex 测试账户；可检查测试数据库和普通控制台输出。

### 操作步骤

1. 查看设置列表、编辑页、总览、错误卡片。
2. 以无效 Key 触发 401 并查看错误。
3. 搜索 SQLite、应用普通日志和截图文字中是否含 `sk-test-xxxxxxxx`。

### 预期结果

1. UI 只显示密码输入框和“留空表示不修改”，从不回显完整 Key。
2. SQLite 只保存 `key_ref` 类引用，不保存 Key 明文。
3. 错误与日志不含 Authorization 头或完整 Key；两个同名账户凭据互不覆盖。

### 失败判定

- 任意界面、数据库或普通错误日志发现完整测试 Key，或同名账户相互串 Key 即失败。

## TC-045 旧凭据迁移失败提示

- 模块：启动迁移、设置提示
- 优先级：P1
- 测试类型：异常、安全
- 使用场景：用户从旧版升级，旧凭据引用在系统凭据库已不可读取。
- 前置条件：构造旧 `provider_<name>` 格式 key_ref 且对应凭据读取失败的测试数据库。

### 操作步骤

1. 启动应用。
2. 进入设置查看迁移提示。
3. 编辑受影响账户重新输入虚拟新 Key，保存并刷新。

### 预期结果

1. 应用不因迁移失败而启动失败。
2. 设置页清晰显示受影响账户数量与重新录入建议。
3. 重新录入后账户可恢复刷新，不影响其他迁移成功账户。

### 失败判定

- 失败凭据被静默删除、没有提示，或迁移错误泄露旧 Key 即失败。

## TC-046 多币种/credits 汇总隔离

- 模块：总览汇总、费用概览
- 优先级：P1
- 测试类型：正常、边界
- 使用场景：用户同时有人民币 DeepSeek/SiliconFlow、美元 OpenRouter/OpenAI 和 Codex credits。
- 前置条件：Mock/真实数据为上述账户返回不同 currency 的余额与费用。

### 操作步骤

1. 刷新全部账户。
2. 查看“今日汇总”和“费用概览”。
3. 手工核对每个币种下的总额。

### 预期结果

1. 同币种余额和费用分别正确求和。

## TC-047 趋势账户快速切换与删除

- 模块：趋势 Widget、异步状态
- 优先级：P1
- 测试类型：异常、UI
- 使用场景：用户快速切换多个账户后删除当前选中的账户。

### 失败判定

## TC-048 Windows/macOS 权限和通知降级

- 优先级：P1

- 使用场景：用户第一次安装时拒绝通知权限，之后仍需正常使用监控。
- 前置条件：Windows 与 macOS 各准备一台可运行构建产物的测试机；通知权限先设为拒绝。

### 操作步骤

1. 触发低额度条件并拒绝/保持拒绝通知权限。

## TC-050 真实日常混合场景回归

- 模块：端到端核心流程
- 优先级：P1
- 测试类型：正常、网络、稳定性
- 使用场景：用户开机后监控三个账户：DeepSeek 正常、OpenRouter 限流、Codex 登录失效；午后网络恢复并修复 Codex。
- 前置条件：配置三个测试账户；Mock/网络分别满足该状态；已设置个人主题、布局和 Mini 位置。

### 操作步骤

1. 启动应用，等待自动刷新并观察三张卡片。
2. 切到 Mini 后通过托盘显示 Full，手动刷新。
3. 恢复 OpenRouter，执行 `codex login` 后刷新 Codex。
4. 重启应用，查看配置和历史趋势。

### 预期结果

1. DeepSeek 正常显示；OpenRouter 与 Codex 各自显示可行动错误，彼此隔离。
2. 窗口模式/托盘流程可用，重复刷新不叠加。
3. 网络与登录恢复后两个失败账户各自恢复，历史只记录成功结果。
4. 重启后账户、主题、布局、窗口位置与有效历史仍保留。

### 失败判定

- 任一单账户问题导致整体不可用、恢复后状态错误、历史污染或配置丢失即失败。

# 测试覆盖总结

核心监控链路已被充分覆盖：账户/凭据生命周期、六类已注册 Provider 的典型接口差异、批量与单账户刷新、前后台调度、网络失败隔离、SQLite 历史与预测、通知阈值，以及窗口与托盘的日常操作。

风险最高的区域是第三方 Provider 接口稳定性与权限差异（尤其 Codex 内部端点、Claude/OpenAI 管理员接口、SiliconFlow 实验性端点）、系统凭据库在不同操作系统上的行为、以及长时间运行下的原生窗口/网络变化。发布前应优先执行 TC-003、TC-004、TC-007、TC-017、TC-019～TC-026、TC-029、TC-034～TC-045、TC-050。

仍有盲区：真实 macOS 打包和签名更新、不同企业代理实现、真实生产 API 的限流策略与费用时间口径，以及尚未实现的备份恢复、诊断导出、完整 DIY 样式和 Widget 自由布局。
